# CRAG Web Console - Stitch 设计 PRD

## 1. 文档目标

本 PRD 用于指导 Stitch 生成 CRAG Web Console 的高保真 Web 设计稿。设计稿需要覆盖管理控制台与独立知识检索对话页，并提供可供 React + Ant Design 实现的完整页面、组件和状态设计，而不是只呈现理想成功态。

## 2. 产品定位

CRAG Web Console 是面向知识库所有者的工作型管理后台。用户可以注册和登录，创建知识库、上传并观察文档摄取状态、管理 API Key，并使用 API Key 在独立 Chat 页面验证知识检索效果。

产品首先服务日常管理与调试，不采用营销落地页结构。视觉应安静、清晰、紧凑，适合高频扫描和重复操作。

## 3. 用户与核心任务

主要用户是知识库 OWNER，核心任务如下：

1. 注册或登录控制台。
2. 创建并查看知识库。
3. 上传 `.txt` 或 `.md` 文档，并观察摄取结果。
4. 在知识库就绪后创建和维护 API Key。
5. 从独立 API Key 页面按 Key 视角检索，并返回所属知识库。
6. 在 Chat 页面输入 API Key，验证问答结果与引用来源。

当前版本不设计成员与租户管理、知识库删除、文档删除、聊天历史、用量统计。

## 4. 信息架构

登录后使用固定左侧导航和顶部工具栏：

- Knowledge
- API Keys
- Chat
- Account

路由与页面：

- `/login`：登录
- `/register`：注册
- `/app/knowledge`：知识库列表
- `/app/knowledge/:knowledgeBaseId`：知识库详情
- `/app/api-keys`：API Key 独立索引
- `/app/chat`：知识检索对话

知识库详情使用三个页签：Overview、Documents、API Keys。

## 5. 全局设计方向

- 以桌面端为主，同时给出平板和移动端关键页面。
- 使用 Ant Design 的布局、表单、表格、页签、标签、抽屉、模态框和反馈模式。
- 页面强调信息密度和操作效率，不使用超大 Hero、装饰性渐变、漂浮色块或层层嵌套卡片。
- 页面区块使用自然留白与分隔线组织；卡片仅用于真正独立的重复项目或工具区域。
- 状态颜色保持一致：处理中为蓝色，就绪为绿色，警告为橙色，失败和危险操作为红色，禁用为中性灰。
- 危险操作必须二次确认，并清楚显示影响对象。
- 图标按钮使用 Ant Design Icons，陌生图标提供 Tooltip。
- 所有页面包含加载、空数据、失败、权限不足与操作反馈状态。
- 文案简洁直接，避免在页面内大段解释产品功能或操作方法。

## 6. 页面设计要求

### 6.1 登录与注册

采用窄宽度居中表单，不设计营销区域。

登录字段：邮箱、密码。注册字段：邮箱、密码、确认密码。包含字段校验、提交中状态、认证失败提示、注册链接或登录链接。移动端表单保持舒适边距，键盘弹出后主要操作仍可访问。

### 6.2 Knowledge 列表

页面顶部包含标题、搜索和“创建知识库”主操作。主体使用紧凑表格，显示：

- 名称
- 创建时间
- API Key 就绪状态
- 行操作

点击名称或整行进入详情。设计创建知识库模态框，并覆盖首次使用空态、列表加载、搜索无结果和接口失败状态。

### 6.3 Knowledge 详情

页头显示返回入口、知识库名称、ID、状态和必要操作，下方为 Overview、Documents、API Keys 页签。

当 `apiKeyReady=false` 时显示明显但不过度打断的警告：文档仍可上传，创建 API Key 按钮保持禁用，并清楚显示等待状态。Overview 展示基本信息与文档状态摘要，不增加后端尚未提供的统计指标。

### 6.4 Documents

提供拖拽上传区和文件选择按钮，明确接受 `.txt`、`.md`、UTF-8、单文件不超过 10 MiB。列表显示文件名、摄取状态、更新时间、失败原因和可用操作。

状态至少包括 PENDING、PROCESSING、READY、FAILED。处理中自动刷新但布局不得跳动。只有后端标记为可重试的失败才显示重试操作。覆盖上传中、上传拒绝、摄取失败、可重试失败和列表为空状态。

### 6.5 API Keys

Knowledge 页签和独立索引页共享一致的数据表达。列表显示名称、Key 前缀、状态、所属知识库、过期时间和操作。独立索引中的知识库名称可返回对应 Knowledge 详情。

当前后端只提供按知识库查询 API Key 的接口，因此独立索引页应使用已有 Knowledge 列表与各知识库 Key 列表组合数据，不要求 Stitch 设计后端不存在的租户级搜索、排序或统计能力。数据量扩大后的租户级索引接口属于后续演进。

状态包括 ACTIVE、DISABLED、REVOKED。操作包括创建、启用、禁用、轮换和撤销，并根据状态控制可用性。

创建或轮换成功后，完整 Key 只在一次性模态框出现：默认遮挡，提供显隐、复制以及“我已保存”确认。关闭后不能再次查看。撤销属于高风险操作，需要二次确认并显示 Key 名称和前缀。

### 6.6 Chat

Chat 是独立工作区，风格接近现代 LLM Chat，但保持管理工具的克制感。页面包含：

- API Key 输入与连接状态
- 用户和助手消息流
- 固定在底部的输入框与发送操作
- 助手答案后的来源引用区

API Key 仅用于当前页面会话，不显示知识库选择，也不要求用户输入知识库 ID。设计初始空态、发送中、无检索结果、Key 无效、服务不可用和可重试错误。引用来源需要可扫描，避免用大卡片挤压对话空间。

### 6.7 Account 与会话状态

顶部工具栏提供账户菜单和退出操作。会话恢复期间显示稳定的应用加载状态；认证失效后回到登录页，并保留简短明确的提示。

## 7. 响应式要求

至少输出以下移动端设计：登录、Knowledge 列表、Knowledge 详情/Documents、Chat。

- 左侧导航折叠为抽屉或移动导航。
- 表格在窄屏改为结构化列表，不依赖横向滚动完成主要操作。
- Chat 输入区固定时不得遮挡最后一条消息。
- 长名称、Key 前缀、错误信息和状态标签不得溢出容器。
- 触控操作保持足够点击面积，高风险操作不与常用操作紧邻。

## 8. Stitch 输出要求

请生成：

1. 桌面端完整页面和关键交互状态。
2. 指定关键页面的移动端版本。
3. 可复用组件及其状态变体，包括导航、表格/列表、状态标签、空态、错误提示、上传区、一次性密钥模态框、消息与引用。
4. 颜色、字号、间距、边框、阴影和响应式规则说明，并尽量映射 Ant Design Token。
5. 页面间跳转、模态框、抽屉、确认操作和禁用条件说明。

设计稿必须覆盖成功态、空态、加载态和主要失败态，并保持页面结构可被 React + Ant Design 直接实现。
